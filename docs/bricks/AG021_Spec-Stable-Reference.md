CLAUDE:

Good question. This is the classic stable reference problem. Let's explore the options:

  Current Approach: Direct ID Reference

  @implements("S-AUTH-001")
  def authenticate(...):
      ...

  Mechanism: String literal pointing to spec ID

  Pros:
  - Unambiguous (globally unique ID)
  - Machine-parsable (no resolution needed)
  - Works across files/modules

  Cons:
  - Opaque (what does S-AUTH-001 mean?)
  - Brittle to ID changes
  - No IDE support (can't jump to definition)

  Workflow when renaming:
  # Rename S-AUTH-001 → S-AUTH-100
  $ jigy refactor rename S-AUTH-001 S-AUTH-100
  # Tool updates:
  # - jig/specs/auth.md frontmatter
  # - All @implements("S-AUTH-001") → @implements("S-AUTH-100")
  # - All @verifies("S-AUTH-001") → @verifies("S-AUTH-100")

  ---
  Option 2: Semantic Path

  @implements("auth.token_expiration")
  def authenticate(...):
      ...

  Mechanism: Hierarchical name (like module path)

  Pros:
  - Human-readable
  - Follows Python naming conventions
  - More stable (semantic name less likely to change than arbitrary ID)

  Cons:
  - Need mapping: semantic path → spec ID
  - Potential collisions (two specs with same semantic name?)
  - Still breaks if semantic name changes

  Mapping file:
  # jig/spec-registry.yaml
  auth.token_expiration: S-AUTH-001
  auth.rate_limiting: S-AUTH-002
  cli.help_text: S-CLI-001

  Workflow:
  # Developer writes semantic name
  @implements("auth.token_expiration")

  # Tool resolves at build time:
  # 1. Look up "auth.token_expiration" → S-AUTH-001
  # 2. Store resolved ID in graph

  ---
  Option 3: File + Anchor

  @implements("specs/auth.md#token-expiration")
  def authenticate(...):
      ...

  Mechanism: Relative file path + heading anchor

  Pros:
  - Shows where spec lives
  - Anchors can be stable (URL-style slugs)
  - Works like markdown links

  Cons:
  - Brittle to file moves
  - Verbose
  - Anchor might change if heading changes

  Spec file:
  <!-- specs/auth.md -->
  ---
  id: S-AUTH-001
  slug: token-expiration
  ---

  ## Token Expiration {#token-expiration}

  Tokens expire after 15 minutes...

  Resolution:
  1. Parse file path → find specs/auth.md
  2. Find heading with anchor token-expiration
  3. Extract id: S-AUTH-001 from frontmatter

  ---
  Option 4: Symbol Import (Generated)

  from jig.specs.auth import S_AUTH_001

  @implements(S_AUTH_001)
  def authenticate(...):
      ...

  Mechanism: Generate Python constants from specs

  Pros:
  - IDE support (autocomplete, go-to-definition)
  - Refactoring tools work (rename symbol)
  - Type-safe (IDE catches typos)
  - No string literals

  Cons:
  - Generated code in repo (or build step)
  - Import overhead
  - Python syntax limits (no hyphens in identifiers)

  Generated file:
  # Generated by jigy index
  # jig/specs/__init__.py

  # Authentication specs
  S_AUTH_001 = "S-AUTH-001"  # Token expiration
  S_AUTH_002 = "S-AUTH-002"  # Rate limiting

  # CLI specs
  S_CLI_001 = "S-CLI-001"  # Help text

  Workflow:
  $ jigy index
  # Generates jig/specs/__init__.py

  # IDE now knows about S_AUTH_001
  # Autocomplete works
  # Refactoring works

  ---
  Option 5: Stable Slug + ID (Hybrid)

  @implements("auth:token-expiration")  # S-AUTH-001
  def authenticate(...):
      ...

  Mechanism: Stable semantic slug, ID in comment for humans

  Pros:
  - Human-readable slug
  - Slug more stable than ID (semantic)
  - Comment shows resolved ID (for debugging)
  - Tool can keep comment in sync

  Cons:
  - Still need slug → ID mapping
  - Comment can drift from reality

  Spec file:
  ---
  id: S-AUTH-001
  slug: auth:token-expiration
  ---
  # Token Expiration

  Tool behavior:
  $ jigy impl rebuild
  # Reads @implements("auth:token-expiration")
  # Looks up slug → S-AUTH-001
  # Updates comment if wrong: @implements("auth:token-expiration")  # S-AUTH-001

  ---
  Option 6: Content Hash (Git-style)

  @implements("spec:4f8a92bc")  # Token expiration
  def authenticate(...):
      ...

  Mechanism: Hash of spec content → stable even if ID changes

  Pros:
  - Truly stable (content-addressed)
  - Rename spec freely, hash doesn't change (unless content changes)
  - Git-like philosophy

  Cons:
  - Completely opaque to humans (need comment)
  - Hash changes when spec content changes (is this bad or good?)
  - Need hash → spec ID mapping

  Resolution:
  # Tool computes hash of spec content
  spec_content = "Tokens expire after 15 minutes of inactivity"
  spec_hash = sha256(spec_content)[:8]  # "4f8a92bc"

  # Lookup table:
  {
    "4f8a92bc": "S-AUTH-001",
    "a3c7d14e": "S-AUTH-002"
  }

  ---
  Option 7: No Decorator (Comment Convention)

  def authenticate(...):
      """
      Authenticate user and return session token.

      Implements: S-AUTH-001, S-AUTH-002
      """
      ...

  Mechanism: Structured docstring

  Pros:
  - No magic decorator
  - Standard Python (docstring always there anyway)
  - Human-readable documentation

  Cons:
  - Harder to parse (need docstring parser)
  - Easy to forget
  - No linter/IDE support

  Parsing:
  # Tool parses docstrings looking for "Implements: ..." pattern
  import ast

  def extract_implements(func_node):
      docstring = ast.get_docstring(func_node)
      if docstring and "Implements:" in docstring:
          line = [l for l in docstring.split("\n") if "Implements:" in l][0]
          spec_ids = [s.strip() for s in line.split("Implements:")[1].split(",")]
          return spec_ids
      return []

  My Recommendation: Hybrid Approach

  Use stable slugs with ID in comment, plus tool support:

  @implements("auth:token-expiration")  # S-AUTH-001
  @implements("auth:rate-limiting")     # S-AUTH-002
  def authenticate(user: str, password: str) -> Token:
      ...

  Why this works:

  1. Human-readable slug - Developer sees auth:token-expiration, knows what it means
  2. Stable - Semantic slug less likely to change than arbitrary ID
  3. ID for debugging - Comment shows resolved ID if you need it
  4. Tool keeps in sync - jigy impl rebuild updates comments if slug resolution changes
  5. Flexible - Can use ID directly if you want: @implements("S-AUTH-001")

  Spec file:
  ---
  id: S-AUTH-001
  slug: auth:token-expiration
  ---
  # Token Expiration

  Tokens expire after 15 minutes of inactivity.

  Renaming workflow:

  Scenario 1: Change slug (semantic rename)
  # Before
  slug: auth:token-expiration

  # After
  slug: auth:session-timeout

  $ jigy impl rebuild
  # Detects slug change
  # Updates all @implements("auth:token-expiration") → @implements("auth:session-timeout")
  # Or warns and requires explicit migration

  Scenario 2: Change ID (re-numbering)
  # Before
  id: S-AUTH-001
  slug: auth:token-expiration

  # After
  id: S-AUTH-100
  slug: auth:token-expiration  # Slug unchanged!

  $ jigy impl rebuild
  # Slug unchanged → no code changes needed
  # Just updates comments: # S-AUTH-001 → # S-AUTH-100

  Slug syntax conventions:
  - subsystem:feature - two-level hierarchy
  - subsystem:component:feature - three-level for complex systems
  - Use kebab-case (URL-friendly)
  - Must be unique across project

  Fallback: If no slug defined, ID is the slug:
  @implements("S-AUTH-001")  # No slug in spec → use ID

  Validation:
  $ jigy validate
  Error: Duplicate slug "auth:token-expiration"
    Found in: S-AUTH-001, S-AUTH-005
    Fix: Change slug in one of the spec files
