# DEBUG Workflow (JIG Edition)

**Version:** 1.0.0 (JIG-integrated)
**Owner:** Jim Meyer
**Audience:** Human developers + AI coding agents (AIA)
**Intent:** Systematic debugging with Intent Graph alignment. Capture what we learned about constraint violations for harvest into OSTC.

---

## 0) What Makes Debugging Different in JIG?

**Debugging is constraint violation discovery.**

When code breaks, one of two things happened:
1. **Implementation violated Intent** - Code/Tests don't satisfy existing O/S constraints
2. **Intent was incomplete/wrong** - O/S constraints don't capture reality

**JIG debugging workflow:**
- Start with **symptoms** (what's broken)
- Identify **violated constraints** (which O/S nodes are misaligned)
- Find **root cause** (where reality diverged from Intent)
- **Fix** the violation (update Code/Tests OR update Intent)
- **Harvest learnings** (capture what we learned about our constraints)

**Key difference from PLAN:**
- PLAN: Known constraints → implementation (constraint satisfaction)
- DEBUG: Broken behavior → find violated/missing constraints (constraint discovery)

---

## 1) Purpose

Create a minimal, systematic process for debugging that:

* Captures **symptoms** clearly (what's broken, how to reproduce)
* Maps symptoms to **violated OSTC constraints** (which Intent nodes are misaligned?)
* Identifies **root cause** (implementation bug OR Intent gap)
* Documents **fix** with traceability to Intent Graph
* Harvests **learnings** into OSTC (new constraints, updated specs, missing tests)
* Creates **RETRO** (why did this happen? what constraint was missing upstream?)

**Philosophy:** Bugs reveal gaps in our constraint model. Every bug is an opportunity to strengthen the Intent Graph.

## 2) JIG Context: Where DEBUG Lives

```
jig/
├── outcomes/              # Why we build (may need updates after debug)
├── specifications/        # What we build (may need updates after debug)
└── deltas/
    ├── active/
    │   └── debug-[issue-id]/
    │       └── DEBUG_[issue-title].md     # ← YOUR DEBUG SESSION LIVES HERE
    └── archive/
        └── debug-[issue-id]/              # Moved after fix merged

src/                       # Code with bugs (and @jig annotations)
tests/                     # Tests that should have caught this (and @jig annotations)
```

**Key Points:**
- Create DEBUG delta when starting investigation: `jig delta new --type debug`
- DEBUG is a temporal artifact (like PLAN)
- Intent (O, S) may get updated based on learnings
- Tests (T) and Code (C) get fixed with `@jig` annotations
- Harvest extracts lessons learned before archiving

---

## 3) When to Use DEBUG vs PLAN

| Scenario | Use DEBUG | Use PLAN |
|----------|-----------|----------|
| Production bug reported | ✅ | ❌ |
| Test failing in CI | ✅ | ❌ |
| Unexpected behavior found | ✅ | ❌ |
| Performance regression | ✅ | ❌ |
| Known feature request | ❌ | ✅ |
| Planned refactor | ❌ | ✅ |
| Exploratory spike | ❌ | ✅ |

**Rule:** If the work starts with "something is broken", use DEBUG. If it starts with "we want to build X", use PLAN.

## 4) Inputs

* **Symptom Report** - Bug ticket, user report, failing test, stack trace
* **Existing Intent Graph** - O/S nodes that should govern this behavior
* **Reproduction Steps** - How to observe the broken behavior
* **Expected vs Actual** - What should happen vs what does happen

---

## 5) Primary Output Artifacts

* **DEBUG Delta** - Investigation notes, root cause, fix, learnings, JIG markers
* **Fix Commit(s)** - Code/test changes with traceability to Intent
* **Updated Intent** - New or modified O/S nodes based on learnings
* **RETRO** - Why did this happen? What constraint was missing?
* **Harvest Report** - Generated by `jig extract`, feeds `jig ai-synthesize`

## 7) Execution Workflow (Constraint-Violation Discovery)

### Phase 1: Triage & Setup (15-30 min)

1. **Create DEBUG branch and delta**
   ```bash
   git checkout -b debug-issue-42
   jig delta new --type debug --issue 42
   # Creates: jig/deltas/active/debug-issue-42/DEBUG_[title].md
   ```

2. **Fill Symptoms section**
   - Clear description of what's broken
   - Reproduction steps (must be specific!)
   - Expected vs actual behavior
   - Impact assessment

3. **Map to Intent Graph**
   - Which O/S nodes should govern this behavior?
   - Which T nodes should have caught this?
   - Initial hypothesis: Intent wrong or Reality wrong?

4. **Commit initial DEBUG**
   ```bash
   git add jig/deltas/
   git commit -m "debug: start investigation for issue #42

   Symptom: [one-line summary]
   Affected subsystem: [name]
   See: jig/deltas/active/debug-issue-42/DEBUG_[title].md"
   ```

### Phase 2: Investigation (variable time)

1. **Reproduce the bug**
   - Follow reproduction steps exactly
   - Document what you observe
   - Capture logs, stack traces, data

2. **Add Investigation Log entries**
   - Timestamp each investigation step
   - Document what you tried and what you found
   - Update DEBUG delta as you go (commits optional during investigation)

3. **Identify violated constraints**
   - Which Specification is violated? (or missing?)
   - Which Tests should have caught this? (or missing?)
   - Which Code location is the root cause?

4. **Find root cause**
   - Add "Root Cause Found" log entry
   - Document: what's broken, why it happened, evidence
   - Map to OSTC: constraint violated, wrong, or missing?

5. **Update Constraint Mapping section**
   - Mark which O/S nodes are violated
   - Identify missing tests
   - Clarify hypothesis: fix Intent or fix Reality?

### Phase 3: Fix (TDD if possible)

1. **Plan the fix**
   - Fill "Fix Strategy" section
   - List required changes (code, tests, intent, docs)
   - Assess risk and rollback plan

2. **Write regression test FIRST** (if not hotfix)
   ```python
   # @jig T-XXX-NNN verifies:S-XXX-NNN subsystem:name
   def test_regression_issue_42():
       """Regression test for issue #42"""
       # This test should FAIL before the fix
       # This test should PASS after the fix
   ```

3. **Implement the fix**
   - Minimal change to satisfy constraints
   - Add/update `@jig` annotations
   - Follow existing code style

4. **Update Intent if needed**
   - Create new O/S nodes if constraints were missing
   - Update existing O/S nodes if constraints were incomplete
   - Document in "Intent Updates" section

5. **Fill Discoveries & Learnings section**
   - Focus on what you learned about the constraint model
   - Add JIG markers for harvestable insights:
     - `#DISCOVERY` - constraint gaps revealed by bug
     - `#LEARNED` - patterns for preventing similar bugs
     - `#DECISION` - tradeoffs made in fix approach

6. **Commit the fix**
   ```bash
   git add src/ tests/ jig/
   git commit -m "fix(subsystem): resolve issue #42

   Root cause: [one-line explanation]
   Fix: [what changed]
   Implements: S-XXX-NNN
   Adds: T-XXX-NNN (regression test)

   See: jig/deltas/active/debug-issue-42/DEBUG_[title].md"
   ```

### Phase 4: RETRO & Harvest

1. **Fill RETRO section**
   - Why did this happen?
   - Where in the process should it have been caught?
   - What would have prevented it?
   - Process improvements proposed

2. **Fill Completion Summary**
   - Changes delivered
   - Constraint alignment achieved
   - Time metrics
   - Harvest preparation (marker counts, proposed OSTC nodes)

3. **Validate the fix**
   - Run reproduction steps (should now work)
   - Run regression test (should pass)
   - Run full test suite (should pass)
   - Run `jig validate --check-all` (should pass)

4. **Harvest learnings**
   ```bash
   jig ai-distill --branch debug-issue-42
   # Extracts markers, proposes OSTC updates, human reviews
   ```

5. **Commit harvest**
   ```bash
   git add jig/
   git commit -m "harvest: learnings from issue #42 debug

   Distilled N markers into M OSTC nodes:
   - S-XXX-042 (NEW): Input validation requirements
   - S-XXX-001 (UPDATE): Added error handling constraints
   - T-XXX-043 (NEW): Regression test

   See: jig/harvest-reports/debug-issue-42-2025-11-18.yaml"
   ```

6. **Merge and archive**
   ```bash
   git checkout main
   git merge debug-issue-42
   jig delta archive --branch debug-issue-42 --retention long-term
   # Archives to: jig/deltas/archive/debug-issue-42/
   ```

## 8) JIG Marker Usage in DEBUG

### Focus on Constraint Model Learnings

**DISCOVERY** - Constraints that were missing or wrong:
```markdown
#DISCOVERY "Specification S-AUTH-001 missing constraint: tokens must validate in constant time"
#DISCOVERY "Edge case not documented: what happens when device_id is null?"
#DISCOVERY "Need new outcome O-XXX-007: System degrades gracefully under invalid input"
```

**LEARNED** - Prevention patterns:
```markdown
#LEARNED "Always add null checks for optional parameters at API boundary"
#LEARNED "Integration tests needed for multi-step workflows - unit tests insufficient"
#LEARNED "Error case acceptance criteria should be explicit in specifications"
```

**DECISION** - Fix approach tradeoffs:
```markdown
#DECISION "Add validation vs trust callers"
**Choice:** Add defensive validation at every entry point
**Rationale:** Safety > performance for this critical path
**Tradeoffs:** +2ms latency per call, acceptable for data integrity guarantee
```

### When to Use Markers in DEBUG

**Use markers for:**
- Constraint gaps revealed by the bug (missing/incomplete O/S nodes) → `#DISCOVERY`
- Prevention patterns learned (how to avoid this class of bug) → `#LEARNED`
- Fix approach decisions with tradeoffs → `#DECISION`
- Process improvements identified in RETRO → `#LEARNED`
- Upstream gaps (PLAN/review/testing process) → `#DISCOVERY`

**Don't marker:**
- Routine investigation steps
- Obvious findings
- Things already in Intent Graph
- Temporary debugging notes

**Aim for:** 3-7 high-value markers per DEBUG session (focus on harvest value)

## 10) Operating Rules (DEBUG + JIG)

**Severity-based rules:**
- **P0/Critical:** Fix first, document after (but still create minimal DEBUG delta for harvest)
- **P1/High:** Create DEBUG delta, investigate, fix with full workflow
- **P2/Medium:** Full DEBUG workflow
- **P3/Low:** Consider batching, full workflow when addressed

**Constraint alignment rules:**
- **ALWAYS map symptoms to Intent Graph** - which O/S nodes are violated/missing?
- **Update Intent when wrong** - if bug reveals wrong constraint, fix the constraint
- **Add Intent when missing** - if bug reveals missing constraint, create the constraint
- **Regression test required** - every bug fix needs a test that would have caught it
- **Harvest before close** - run `jig ai-distill` before archiving DEBUG delta

**Annotation rules:**
- **Mark regression tests:** `# @jig T-XXX-NNN verifies:S-YYY-NNN subsystem:name`
- **Mark fixed code:** `# @jig C-XXX-NNN implements:S-YYY-NNN subsystem:name`
- **Link commits to DEBUG:** Use trailers `See: jig/deltas/active/debug-NNN/`

**RETRO rules:**
- **RETRO required for P0/P1** - why did this escape? what process failed?
- **RETRO recommended for P2/P3** - capture learnings for prevention
- **RETRO feeds process improvement** - harvest RETRO discoveries into team practices

## 12) DEBUG vs PLAN Comparison

| Aspect | PLAN | DEBUG |
|--------|------|-------|
| **Trigger** | Known feature/requirement | Something is broken |
| **Starting point** | SCOPE (known Intent) | Symptoms (unknown cause) |
| **Direction** | Constraints → Implementation | Behavior → Violated constraints |
| **Intent lifecycle** | Create Intent upfront (WU0) | Discover Intent gaps during investigation |
| **Uncertainty** | Low (requirements known) | High (cause unknown) |
| **Time pressure** | Normal sprint cadence | Often urgent (especially P0/P1) |
| **Primary artifact** | PLAN with Work Units | DEBUG with Investigation Log |
| **TDD emphasis** | Strong (write tests first) | Medium (regression test after root cause) |
| **Markers focus** | Discoveries during implementation | Constraint gaps revealed by bug |
| **Harvest value** | New features → new Intent | Bug lessons → strengthened Intent |

**Both share:**
- JIG markers (`#DISCOVERY`, `#LEARNED`, `#DECISION`)
- Harvest workflow (`jig ai-distill`)
- OSTC alignment (`jig validate`)
- Traceability (commits reference deltas)
- Archive after completion

## Investigation Log

### 2025-11-18 14:23 - Root Cause Found

**Root cause:** Token validation compares device_id without null check. Second login sets device_id, first login has null device_id, comparison throws exception, token rejected.

**Why:** Spec S-AUTH-001 didn't specify device_id as required field.

**Evidence:** `src/auth.py:156` - `if token.device_id == device_id:` fails when token.device_id is None

## Fix Strategy

- Add null check to device_id validation
- Make device_id required in token claims
- Add regression test for null device_id

## Implementation

```python
# @jig C-AUTH-012 implements:S-AUTH-001 subsystem:auth
def validate_token(token: str, device_id: str) -> bool:
    claims = decode_token(token)
    # FIX: Handle null device_id
    if claims.device_id is None or device_id is None:
        return False
    return claims.device_id == device_id
```

def test_regression_null_device_id():
