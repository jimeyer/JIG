# GOSTC v2: Annotation-Driven Software Documentation

**Purpose**: Create a complete GOSTC (Graph of Outcomes, Specifications, Tests, and Code) representation that eliminates redundancy by treating documentation and implementation differently.

**Core Principle**: Only conceptual layers (Outcomes, Specifications) exist as separate documentation files. Implementation layers (Tests, Code) are tracked through lightweight annotations in the actual source code.

---

## Part 1: Understanding GOSTC v2

### The 4-Layer Model

GOSTC treats software as four aligned layers, but distinguishes between **intent** and **reality**:

```
Intent Layers (Documentation Files):
O (Outcomes)        ← WHY: Business goals, user needs
    ↕ satisfies
S (Specifications)  ← WHAT: Technical requirements, contracts

Reality Layers (Code Annotations):
T (Tests)           ← VERIFY: Validation, acceptance criteria
    ↕ validates/covers
C (Code)            ← HOW: Implementation
```

### Key Innovation: Two Types of Nodes

| Type | Storage | Reason | Maintained By |
|------|---------|--------|---------------|
| **O, S** | Individual `.md` files | Conceptual - no code equivalent | Human (manual) |
| **T, C** | Annotations in code → Generated indices | Implementation - has actual code | Human (annotations) + Tool (generation) |

**Why This Matters**: 
- You write a test → it already describes what it does (docstring + code)
- You write a function → it already describes what it does (docstring + code)
- GOSTC just adds **relational metadata** (implements what? validates what?)

```
└── .gostc.toml                     # Configuration (optional)
```

**Manual files**: O-*.md, S-*.md (the "why" and "what")  
**Generated files**: Everything in `generated/` (derived from code)

### Code Annotations (NEW!)

**In source code files** - Add single-line annotations above functions/classes:

```python
# expense_tracker.py

# @gostc C-001 implements:S-001,S-002
def validate_expense(amount, category):
    """
    Validate expense data before storage.
    
    Args:
        amount: Dollar amount (must be positive)
        category: Expense category (must be in VALID_CATEGORIES)
        
    Returns:
        True if valid
        
    Raises:
        ValueError: If validation fails
    """
    if amount <= 0:
        raise ValueError("Amount must be positive")
    if category not in VALID_CATEGORIES:
        raise ValueError("Invalid category")
    return True


# @gostc C-002 implements:S-003 depends:C-001
class ExpenseTracker:
    """Track and manage personal expenses."""
    
    def __init__(self):
        self.expenses = []
    
    # @gostc C-003 implements:S-003 depends:C-001
    def add_expense(self, amount, category):
        """Add validated expense to tracker."""
        validate_expense(amount, category)
        self.expenses.append({"amount": amount, "category": category})
```

**Annotation Format**:
```
# @gostc <node-id> implements:<spec-ids> depends:<code-ids>
```

**Generated code_index.json**:
```json
{
  "code_nodes": [
    {
      "id": "C-001",
      "title": "validate_expense",
      "location": {
        "file": "expense_tracker.py",
        "line": 4,
        "symbol": "validate_expense",
        "type": "function"
      },
      "docstring": "Validate expense data before storage.",
      "implements": ["S-001", "S-002"],
      "depends_on": []
    },
    {
      "id": "C-003",
      "title": "ExpenseTracker.add_expense",
      "location": {
        "file": "expense_tracker.py",
        "line": 27,
        "symbol": "ExpenseTracker.add_expense",
        "type": "method"
      },
      "docstring": "Add validated expense to tracker.",
      "implements": ["S-003"],
      "depends_on": ["C-001"]
    }
  ]
}
```

### Test Annotations (NEW!)

**In test files** - Add single-line annotations above test functions:

```python
# test_expense_tracker.py

import pytest
from expense_tracker import validate_expense, ExpenseTracker

# @gostc T-001 validates:S-001 covers:C-001
def test_valid_expense_accepted():
    """Test that valid expense passes validation."""
    # Given
    amount = 50.00
    category = "food"
    
    # When
    result = validate_expense(amount, category)
    
    # Then
    assert result is True


# @gostc T-002 validates:S-001 covers:C-001
def test_negative_amount_rejected():
    """Test that negative amount raises ValueError."""
    # Given
    amount = -10.00
    category = "food"
    
    # When/Then
    with pytest.raises(ValueError, match="Amount must be positive"):
        validate_expense(amount, category)


# @gostc T-003 validates:S-001,S-002 covers:C-001
def test_invalid_category_rejected():
    """Test that invalid category raises ValueError."""
    # Given
    amount = 50.00
    category = "invalid"
    
    # When/Then
    with pytest.raises(ValueError, match="Invalid category"):
        validate_expense(amount, category)


# @gostc T-004 validates:S-003 covers:C-002,C-003
def test_add_expense_to_tracker():
    """Test adding expense to tracker after validation."""
    # Given
    tracker = ExpenseTracker()
    
    # When
    tracker.add_expense(50.00, "food")
    
    # Then
    assert len(tracker.expenses) == 1
    assert tracker.expenses[0]["amount"] == 50.00
```

**Annotation Format**:
```
# @gostc <node-id> validates:<spec-ids> covers:<code-ids>
```

```markdown
- Category must be valid

- [x] T-002: test_negative_amount_rejected ✅
- [x] T-003: test_invalid_category_rejected ✅
- [ ] T-004: test_zero_amount_rejected (TODO)
- [ ] T-005: test_boundary_values (TODO)
```

**Option 2: Create Stub Tests**

Create the test function with `@pytest.mark.skip`:

```python
# @gostc T-004 validates:S-001 covers:C-001
@pytest.mark.skip(reason="Not implemented yet")
def test_zero_amount_rejected():
    """Test that zero amount is rejected."""
    pytest.fail("TODO: Implement this test")
```

The test appears in test_index.json with `status: "skipped"`.

## Part 4: Step-by-Step Process

### Step 1: Analyze the Code

Read the source file completely. Understand:
- What problem does it solve?
- What are the main functions/classes?
- What validation rules exist?
- What business logic is implemented?

### Step 2: Extract Outcomes (Top-Down)

**Question**: "Why would someone use this code?"

Create `.gostc/nodes/outcomes/O-001.md` through `O-00X.md` for each major user-facing capability.

**Example**:
```markdown
---
id: O-001
type: O
title: Track personal expenses accurately
---

As a user, I want to record and validate my expenses so that I can maintain accurate financial records.
```

### Step 3: Extract Specifications (From Code)

**Question**: "What are the technical requirements that make these outcomes possible?"

Create `.gostc/nodes/specifications/S-001.md` through `S-00X.md` for each testable requirement.

**Example**:
```markdown
---
id: S-001
type: S
title: Expense validation rules
satisfies: [O-001]
---

## Requirements
- Amount must be positive decimal number
- Category must be in VALID_CATEGORIES list
```

### Step 4: Annotate Code (Bottom-Up)

**Question**: "What does this function implement?"

Add annotations to source code:

```python
# @gostc C-001 implements:S-001
def validate_expense(amount, category):
    """Validate expense data."""
    # ... implementation
```

### Step 5: Annotate Tests (If Exist)

If tests exist, add annotations:

```python
# @gostc T-001 validates:S-001 covers:C-001
def test_valid_expense():
    """Test validation accepts valid input."""
    # ... test code
```

If tests don't exist, document them in S-*.md files under "Test Plan" section.

### Step 6: Generate Indices and Graph

Run the GOSTC tooling:

```bash
gostc scan --source src/ --tests tests/ --output .gostc/generated/
```

This generates:
- `code_index.json` (from code annotations)
- `test_index.json` (from test annotations)
- `graph.json` (all relationships)

## Part 6: Tooling Requirements

### Scanner Tool

**Purpose**: Parse source and test files to extract GOSTC annotations.

```bash
gostc scan [OPTIONS]

Options:
  --source PATH       Directory containing source code
  --tests PATH        Directory containing test files
  --output PATH       Directory for generated files
  --validate          Check for broken references
  --update-specs      Update "Implementation Status" in S-*.md files
```

**What it does**:
1. Scans all Python files for `@gostc` annotations
2. Extracts docstrings, line numbers, signatures
3. Generates `code_index.json` and `test_index.json`
4. Reads O-*.md and S-*.md frontmatter
5. Generates `graph.json` with all edges
6. Optionally updates S-*.md files with current implementation status

### Validator Tool

**Purpose**: Check consistency and completeness.

```bash
gostc validate [OPTIONS]

Options:
  --strict            Fail on any warnings
  --check-coverage    Ensure all specs have tests/code
```

**Checks**:
- ✓ All node IDs are unique
- ✓ All referenced nodes exist (no dangling references)
- ✓ All specifications have at least one implementing code node
- ✓ All specifications have at least one validating test
- ✓ All code nodes reference valid specification IDs
- ✓ File paths in indices actually exist
- ✓ Line numbers are reasonable

### Visualizer Tool

**Purpose**: Generate visual graphs and reports.

```bash
gostc viz [OPTIONS]

Options:
  --format FORMAT     Output format (html, svg, graphviz)
  --from NODE         Trace from specific node
  --to NODE           Trace to specific node
```

**Outputs**:
- Interactive HTML graph
- Traceability matrix
- Coverage reports

## Part 7: Annotation Syntax Reference

### General Format

```
# @gostc <node-id> <key>:<value>,<value> <key>:<value>
```

### For Code Nodes (C-*)

```python
# @gostc C-XXX implements:S-001,S-002 depends:C-005,C-007
def function_name():
    pass

# @gostc C-XXX implements:S-003
class ClassName:
    pass
```

**Keys**:
- `implements:` (required) - Comma-separated spec IDs
- `depends:` (optional) - Comma-separated code IDs this depends on

### For Test Nodes (T-*)

```python
# @gostc T-XXX validates:S-001,S-002 covers:C-001,C-003
def test_function_name():
    pass
```

**Keys**:
- `validates:` (required) - Comma-separated spec IDs
- `covers:` (required) - Comma-separated code IDs

### For Specifications (S-*)

In frontmatter:
```yaml
---
id: S-XXX
satisfies: [O-001, O-002]
---
```

## Part 8: Workflow Examples

### Starting a New Feature

1. **Document intent**:
   ```bash
   # Create O-003.md
   echo "As a user, I want to see spending summaries..."
   
   # Create S-005.md
   echo "System must calculate totals by category..."
   ```

2. **Write tests first (TDD)**:
   ```python
   # @gostc T-010 validates:S-005 covers:C-008
   def test_calculate_category_totals():
       """Test that totals are calculated correctly."""
       # ... test implementation
   ```

3. **Implement code**:
   ```python
   # @gostc C-008 implements:S-005
   def calculate_category_totals(expenses):
       """Calculate spending totals by category."""
       # ... implementation
   ```

4. **Generate graph**:
   ```bash
   gostc scan --source src/ --tests tests/
   ```

5. **Validate**:
   ```bash
   gostc validate
   # ✓ O-003 satisfied by S-005
   # ✓ S-005 implemented by C-008
   # ✓ S-005 validated by T-010
   # ✓ C-008 covered by T-010
   ```

### Refactoring Existing Code

1. **Add annotations to existing code**:
   ```python
   # @gostc C-001 implements:S-001,S-002
   def existing_function():
       """This was already here."""
       pass
   ```

2. **Add annotations to existing tests**:
   ```python
   # @gostc T-001 validates:S-001 covers:C-001
   def test_existing_function():
       """This test already existed."""
       pass
   ```

3. **Scan and generate**:
   ```bash
   gostc scan --source . --tests tests/
   ```

4. **Review generated graph** to find gaps:
   ```bash
   gostc validate --check-coverage
   # ⚠ S-003 has no implementing code
   # ⚠ S-004 has no validating tests
   # ⚠ C-005 not covered by any tests
   ```

1. **Analyze code** to understand business goals

3. **Create S-*.md files** (8-12 specifications)

## Part 9: Benefits Over GOSTC v1

### ✅ No Redundancy

| GOSTC v1 | GOSTC v2 |
|----------|----------|
| Write function | Write function |
| Write C-XXX.md describing function ❌ | Add one-line annotation ✅ |
| Write test | Write test |
| Write T-XXX.md describing test ❌ | Add one-line annotation ✅ |
| Manually maintain graph.json ❌ | Auto-generate graph.json ✅ |

### ✅ Single Source of Truth

- Implementation details: In the actual code (docstrings, comments)
- GOSTC metadata: In annotations (which spec/test)
- Business intent: In O/S markdown files

### ✅ Stays in Sync

```bash
# After any code change:
gostc scan --source . --tests tests/

# Automatically:
# - Updates code_index.json
# - Updates test_index.json
# - Regenerates graph.json
# - Validates all references
```

### ✅ Developer-Friendly

```python
# Minimal annotation - just relationship metadata
# @gostc C-002 implements:S-001,S-003

# Everything else is what you'd write anyway:
def save_prompt(text, tool, project):
    """
    Save prompt to journal file.
    
    Args:
        text: Prompt text to save
        tool: AI tool being used
        project: Project context (optional)
    """
    # Implementation...
```

### ✅ Tool-Enabled

- **IDE integration**: Jump from spec to implementation
- **Coverage reports**: Which specs lack tests?
- **Impact analysis**: What breaks if I change this spec?
- **Onboarding**: New dev reads O/S docs, tools show implementation

## Part 10: Configuration File

**File**: `.gostc.toml` (optional, in project root)

```toml
[gostc]
version = "2.0"

[paths]
source = ["src/", "lib/"]
tests = ["tests/"]
outcomes = ".gostc/nodes/outcomes/"
specifications = ".gostc/nodes/specifications/"
generated = ".gostc/generated/"

[annotation]
format = "python"  # python, javascript, java, etc.
marker = "@gostc"

[validation]
require_tests = true          # All specs must have tests
require_implementation = true # All specs must have code
allow_orphans = false        # No disconnected nodes

[generation]
auto_update_specs = true     # Update "Implementation Status" in S-*.md
include_rationale = true     # Generate rationale for edges
timestamp_format = "iso8601"
```

## Part 13: Key Principles

1. **Separation of Concerns**:
   - Intent (O, S) = Documentation files
   - Reality (T, C) = Code annotations

2. **DRY (Don't Repeat Yourself)**:
   - Don't describe implementation in separate files
   - Code and tests are self-documenting
   - Add only relational metadata

3. **Tool-First**:
   - Humans write O, S, and annotations
   - Tools generate indices and graph
   - Tools validate consistency

4. **Traceable**:
   - Any spec → What implements it?
   - Any code → What spec does it implement?
   - Any test → What does it validate and cover?

5. **Maintainable**:
   - Change code → Run scan → Graph updated
   - Add test → Run scan → Graph updated
   - Refactor → Annotations move with code


```python

# @gostc C-002 implements:S-999
# S-999 doesn't exist

# @gostc T-001 validates:S-001
```
