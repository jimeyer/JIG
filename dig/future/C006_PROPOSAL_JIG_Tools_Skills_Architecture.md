## Core Principle

**"Tools do. Skills know."**

- **Tools** = deterministic CLI commands with structured output for agent consumption
- **Skills** = markdown instructions teaching procedural knowledge that orchestrates tools

## Agent Pain Points (Why This Matters)

When I (Claude Code) land in a JIG project, I face these concrete problems:

### 1. Orientation is Expensive

To understand the JIG landscape, I currently must:
```
Read jig/bricks.yaml           → What bricks exist?
Glob jig/specifications/*.md   → What specs exist?
Read each spec file            → What do they say?
Grep for @jig.implements       → What's implemented?
Grep for @jig.verifies         → What's verified?
```

**This costs 5-10 tool calls and significant context** just to orient myself.

### 2. Relationship Tracing is Manual

The S-F-T triangle is the core abstraction, but I can't query it:

```
"What functions implement S-042?"     → Grep across entire codebase
"What tests verify S-042?"            → Grep again
"What specs are in brick B-crdt?"     → Manual correlation
"What's unverified?"                  → Reconstruct entire graph
```

**I want to query the graph, not reconstruct it from files.**

### 3. Validation Output is Human-Oriented

Current `jigy validate` output:
```
ERROR: S-003 missing required field 'id'
WARNING: F-auth.login has no @jig.implements
```

I can read this, but I can't programmatically act on it. I need:
- Error codes for categorized handling
- File paths and line numbers for editing
- Fix hints I can execute

### 4. Artifact Creation is Error-Prone

Creating a new spec requires:
- Finding next available ID (grep + sort + increment)
- Getting frontmatter format right
- Following evergreen principles
- Not duplicating existing specs

**One command should handle this correctly.**

### 5. Context Overload vs. Context Starvation

Two failure modes:
- **Overload:** Inject all JIG docs at session start → wastes context on irrelevant info
- **Starvation:** Inject nothing → I make mistakes, miss conventions

**I need minimal bootstrap + on-demand deep knowledge.**

## Session Start Context Specification

### Unified Context via `digy context` (Preferred)

When both DIG and JIG are present, the session briefing should come from `digy context` (see D011). This command generates a unified briefing that includes:

```markdown
# Session Context

## Current Work Stream
**Active Plan**: D009 - digy v2 Implementation
- Parent: D004 (CONCEPT: DIG)
- Implementing: S-004, S-005, S-006
- Bricks: CREATE B-digy-core, B-digy-cli

## Boundaries
| Action | Bricks |
|--------|--------|
| CREATE | B-digy-core, B-digy-cli |
| MODIFY | (none) |
| FORBIDDEN | B-protocol-core, B-data-models |

## Relevant Specs
| ID | Title | Status |
|----|-------|--------|
| S-004 | CLI validates frontmatter | implementing |
| S-005 | Validation outputs JSON | implementing |

## Key Decisions (don't contradict)
- **D003**: YAML frontmatter, not JSON
- **D005**: JWT with refresh tokens

## Dead Ends (don't suggest)
- **D007**: GraphQL API → rejected (overkill for CLI)

## JIG Tools Available
- `jigy show specs` — List specifications with status
- `jigy audit gaps` — Find unimplemented/unverified
- `jigy validate --format json` — Structured validation
```

**Why unified context is better:**
- DIG tells me what to work on, what's been decided, what not to suggest
- JIG tells me what must be true, what's implemented, what's verified
- One briefing, complete picture

### JIG-Only Fallback

For projects with JIG but no DIG, inject this minimal JIG context:

```markdown
## JIG Project

This codebase uses JIG for intent-implementation alignment.

**Quick commands:**
- `jigy rebuild` — Regenerate graphs, validate all constraints
- `jigy show specs` — List all specifications with status
- `jigy show bricks` — Show brick/layer structure
- `jigy audit gaps` — Find unimplemented/unverified specs

**Key locations:**
- `jig/specifications/` — Behavioral requirements (S-XXX.md)
- `jig/outcomes/` — Business value groupings (O-XXX.md)
- `jig/bricks.yaml` — Architectural partitioning

**On-demand skills:** `/jigplan`, `/wu`, `/audit-intent`

**Before creating new specs:** Run `jigy show specs` to check for reusable existing specs.
```

### Context Injection Rules

| Project Has | Inject Via | Content |
|-------------|------------|---------|
| DIG + JIG | `digy context` | Unified: work stream, decisions, dead ends, specs, boundaries |
| JIG only | JIG fallback | Minimal: commands, locations, skills reminder |
| DIG only | `digy context` | DIG-only: work stream, decisions, dead ends |

**What NOT to inject (regardless of source):**
- Full S-F-T triangle explanation (load if needed)
- Brick/layer rules (load if working on architecture)
- Evergreen principles (load if writing O/S nodes)
- Complete workflow procedures (load via skills)

## Prioritized Tool Requirements

### P0: Critical (Implement First)

#### 1. Graph Query Command

**The single most valuable tool.** Let me query the JIG graph directly.

```bash
# Show everything about a spec
jigy show spec S-042

# Output (human-readable default):
S-042: CRDT Value Observation
  Outcome: O-012 (Real-time Collaboration)
  Status: PARTIAL

  Implements (2):
    F-crdt.observe.subscribe      src/crdt/observe.py:45
    F-crdt.observe.notify         src/crdt/observe.py:78

  Verifies (1):
    T-test_observe.test_subscribe tests/test_observe.py:23

  Missing:
    - No test for notify() function

  Brick: B-crdt-observe (layer 1)
```

```bash
# JSON mode for programmatic use
jigy show spec S-042 --format json
```

```json
{
  "id": "S-042",
  "title": "CRDT Value Observation",
  "outcome": "O-012",
  "status": "partial",
  "implementations": [
    {"id": "F-crdt.observe.subscribe", "file": "src/crdt/observe.py", "line": 45},
    {"id": "F-crdt.observe.notify", "file": "src/crdt/observe.py", "line": 78}
  ],
  "verifications": [
    {"id": "T-test_observe.test_subscribe", "file": "tests/test_observe.py", "line": 23}
  ],
  "gaps": ["F-crdt.observe.notify has no verifying test"],
  "brick": {"id": "B-crdt-observe", "layer": 1}
}
```

**Other graph queries I need:**

```bash
# Show brick with its specs, functions, dependencies
jigy show brick B-crdt-observe

# Show outcome with its specs and rollup status
jigy show outcome O-012

# List all specs with implementation/verification status
jigy show specs

# List specs filtered by status
jigy show specs --unimplemented
jigy show specs --unverified
jigy show specs --orphan  # no outcome
```

#### 2. Structured Validation Output

```bash
jigy validate --format json
```

```json
{
  "valid": false,
  "summary": {
    "errors": 2,
    "warnings": 1,
    "specs": {"total": 45, "valid": 44},
    "bricks": {"total": 8, "valid": 8},
    "partition": {"covered": 142, "gaps": 3, "overlaps": 0}
  },
  "issues": [
    {
      "severity": "error",
      "code": "MISSING_REQUIRED_FIELD",
      "message": "Specification missing required field 'id'",
      "file": "jig/specifications/S-003.md",
      "line": 1,
      "fix": {
        "action": "add_frontmatter",
        "field": "id",
        "value": "S-003"
      }
    },
    {
      "severity": "error",
      "code": "INVALID_REFERENCE",
      "message": "Decorator references non-existent spec 'S-999'",
      "file": "src/auth/login.py",
      "line": 23,
      "fix": {
        "action": "update_decorator",
        "current": "@jig.implements(\"S-999\")",
        "options": ["S-001", "S-042"]
      }
    },
    {
      "severity": "warning",
      "code": "UNIMPLEMENTED_SPEC",
      "message": "Specification has no implementing functions",
      "file": "jig/specifications/S-044.md",
      "spec_id": "S-044"
    }
  ]
}
```

**Error codes I need:**

| Code | Meaning | Agent Action |
|------|---------|--------------|
| `MISSING_REQUIRED_FIELD` | Frontmatter incomplete | Add field |
| `INVALID_REFERENCE` | Decorator points to non-existent spec | Fix decorator |
| `DUPLICATE_ID` | Two specs with same ID | Rename one |
| `PARTITION_GAP` | Function not in any brick | Add to brick |
| `PARTITION_OVERLAP` | Function in multiple bricks | Remove from one |
| `LAYER_VIOLATION` | Upward dependency | Restructure or re-layer |
| `CLASS_SPLIT` | Class methods in different bricks | Consolidate |
| `UNIMPLEMENTED_SPEC` | Spec has no @jig.implements | Implement or verify intentional |
| `UNVERIFIED_SPEC` | Spec has no @jig.verifies | Add tests |

### P1: High Value (Implement Second)

#### 4. ID Generation

```bash
jigy next-id spec
# Output: S-047

jigy next-id outcome
# Output: O-014

jigy next-id brick --prefix crdt
# Output: B-crdt-003  (or suggest: B-crdt-observe)
```

**Why this matters:** I currently grep + sort + increment manually. This is error-prone and wastes tokens.

#### 5. Artifact Creation Commands

```bash
# Create spec with validation
jigy spec new S-047 "CRDT Garbage Collection" \
  --implements O-012 \
  --body "CRDTs automatically garbage collect tombstones older than 30 days.

**Acceptance Criteria:**
- Tombstones older than gc_threshold are removed
- GC runs on configurable interval
- GC does not remove tombstones with pending syncs"

# Or via stdin for complex bodies
jigy spec new S-047 "CRDT Garbage Collection" --implements O-012 <<'EOF'
CRDTs automatically garbage collect tombstones older than 30 days.

**Acceptance Criteria:**
- Tombstones older than gc_threshold are removed
- GC runs on configurable interval
- GC does not remove tombstones with pending syncs
EOF
```

**Validation on creation:**
- ID format correct
- ID not already used
- Outcome reference valid (if provided)
- Frontmatter complete
- Body follows basic structure

```bash
# Create outcome
jigy outcome new O-014 "Offline-First Experience" \
  --specifies S-044,S-045,S-046 \
  --body "Users can work without network connectivity.

**Value:** Enables field work, reduces sync anxiety."
```

#### 6. Spec Search

```bash
# Find specs by keyword (searches title + body)
jigy search specs "authentication"

# Output:
S-001  Token Expiration           (O-001) [implemented, verified]
S-002  Password Hashing           (O-001) [implemented, unverified]
S-007  Session Invalidation       (O-001) [unimplemented]
```

**Why this matters:** Before creating a new spec, I MUST check if similar specs exist. Currently requires grep + manual reading.

### P2: Nice to Have (Implement Third)

#### 7. Brick Management

```bash
# Add function to brick
jigy brick add-unit B-crdt-observe M-crdt.observe

# Suggest layer for new brick based on dependencies
jigy brick suggest-layer B-crdt-observe
# Output: Layer 1 (depends on B-crdt-core at layer 0)

# Visualize layer structure
jigy layers --tree
```

#### 8. Decorator Insertion Helper

```bash
# Show what decorator to add and where
jigy impl suggest S-047 src/crdt/gc.py

# Output:
Add to src/crdt/gc.py:
  Line 23: @jig.implements("S-047")  # before def garbage_collect()
  Line 45: @jig.implements("S-047")  # before def schedule_gc()
```

## On-Demand Skills

Skills load procedural knowledge when I'm doing specific workflows. **Do not inject at session start.**

### Skill: `/jigplan`

**Trigger:** "create a jigplan", "plan feature X with JIG"

**Loads:**
- O/S reconciliation procedure (REUSE > UPDATE > CREATE)
- Brick scoping rules (CREATE/MODIFY/FORBIDDEN)
- JIGPLAN document template
- Evergreen principles for writing specs

**Orchestrates:**
```bash
jigy show specs              # What exists?
jigy audit gaps              # What's missing?
jigy validate --format json  # Any issues?
jigy spec new ...            # Create new specs
jigy rebuild                 # Validate result
```

### Skill: `/wu`

**Trigger:** "execute work unit N", "implement WU3"

**Loads:**
- TDD workflow (Red → Green → Refactor)
- Brick scope constraints from PLAN
- Escalation rules (when to stop and report)
- Decorator conventions

**Orchestrates:**
```bash
jigy show spec S-XXX         # Understand the spec
jigy validate --format json  # Pre-flight check
# ... implement ...
jigy rebuild                 # Post-flight validation
pytest                       # Run tests
```

### Skill: `/audit-intent`

**Trigger:** "audit the O/S graph", "check intent coverage"

**Loads:**
- Evergreen quality criteria
- Common anti-patterns to detect
- Remediation procedures

**Orchestrates:**
```bash
jigy audit gaps              # Find missing coverage
jigy show specs --orphan     # Specs without outcomes
jigy validate --format json  # Structural issues
```

## Tool Output Design Principles

### 1. Human-Readable Default, JSON for Agents

```bash
jigy show spec S-042           # Human-readable (default)
jigy show spec S-042 --format json  # Agent consumption
```

JSON mode is for agent consumption only. No `--pretty` flag — agents don't need it.

### 2. JSON Format Specification

**Single objects → Compact single-line JSON:**

```bash
jigy show spec S-042 --format json
```
```
{"id":"S-042","title":"CRDT Value Observation","outcome":"O-012","status":"partial","implementations":[{"id":"F-crdt.observe.subscribe","file":"src/crdt/observe.py","line":45}],"verifications":[],"brick":{"id":"B-crdt-observe","layer":1}}
```

**Lists → NDJSON (one object per line):**

```bash
jigy show specs --format json
```
```
{"id":"S-001","title":"Token Expiration","outcome":"O-001","status":"implemented"}
{"id":"S-002","title":"Password Hashing","outcome":"O-001","status":"unverified"}
{"id":"S-003","title":"Session Management","outcome":"O-001","status":"unimplemented"}
```

**Validation → Compact single-line (nested structure):**

```bash
jigy validate --format json
```
```
{"valid":false,"summary":{"errors":2,"warnings":1},"issues":[{"severity":"error","code":"MISSING_REQUIRED_FIELD","file":"jig/specifications/S-003.md","line":1},{"severity":"error","code":"INVALID_REFERENCE","file":"src/auth/login.py","line":23}]}
```

| Output Type | Format | Example Command |
|-------------|--------|-----------------|
| Single object | Compact single-line JSON | `jigy show spec S-042` |
| List of objects | NDJSON (one per line) | `jigy show specs`, `jigy audit gaps` |
| Validation result | Compact single-line JSON | `jigy validate` |

**Why NDJSON for lists:**
- Consistent with `intent-graph.ndjson`, `deliberation-graph.ndjson`
- Grep-friendly: `jigy show specs --format json | grep S-042`
- Streaming: process before full output completes
- Each line independently parseable

**Why compact:**
- Fewer tokens for agent to consume
- No wasted context on whitespace

### 3. Exit Codes are Meaningful

| Exit Code | Meaning |
|-----------|---------|
| 0 | Success, no issues |
| 1 | Validation errors found |
| 2 | Command usage error |
| 3 | File not found / bad reference |

### 4. JSON Output is Complete

JSON output includes everything needed for programmatic action:
- File paths (absolute)
- Line numbers
- Fix suggestions
- Related entity IDs

### 5. Errors Include Fix Hints

Every error should suggest how to fix it:

```json
{
  "code": "MISSING_REQUIRED_FIELD",
  "fix": {
    "action": "add_frontmatter",
    "field": "id",
    "value": "S-003"
  }
}
```
