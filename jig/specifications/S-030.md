# Compute Brick Membership at Query Time

The visualizer MUST compute brick-to-node membership by joining brick units with implementation nodes, per A001 §6.2.

**Acceptance Criteria**:
- Extract brick nodes from intent graph with `units` arrays
- Expand M- prefixed units to all implementation nodes with matching module prefix (e.g., `M-jig.cli` matches `M-jig.cli.main`, `F-jig.cli.main.cli`, etc.)
- Expand C- prefixed units to class node + all method nodes (e.g., `C-auth.Token` matches `C-auth.Token`, `F-auth.Token.__init__`, `F-auth.Token.validate`)
- Expand F- prefixed units to exact function match (e.g., `F-auth.login` matches only `F-auth.login`)
- Return brick membership map: implementation node ID → brick ID
- Validate brick partition constraint per A001 §10: every function belongs to exactly one brick
- Log warnings for partition violations (functions in multiple bricks or no brick)
- Computation happens in memory at query time (no modification to NDJSON files on disk)
- Console logs show membership computation results (count of nodes assigned, validation status)

**Rationale**: A001 §6.2 mandates "Brick assignment SHALL be computed at query time by joining bricks.yaml with graph." This ensures implementation graph remains pure and brick assignments stay synchronized with bricks.yaml source of truth.
