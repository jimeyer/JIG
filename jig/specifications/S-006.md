# Parse errors fail fast with clear file:line reporting

## Constraints

1. **Any AST parse error stops build immediately**
   - No partial graph output on error
   - Exit code 1 (failure)
   - Clear, actionable error message
   - Strict mode: unparseable code means uncertain graph

2. **Error message includes file path and line number**
   - Format: `ERROR: {file_path}:{line}:{column}: {message}`
   - Example: `ERROR: src/jig/core/graph.py:42:5: invalid syntax`
   - Enables editor navigation (most editors support file:line:column format)
   - Includes snippet of problematic code when available

3. **No partial graphs on error (strict mode)**
   - If any file fails to parse, no NDJSON file is written
   - Rationale: Partial graphs are misleading and break downstream analysis
   - Future: Could add `--lenient` mode that skips unparseable files with warning

## Error Handling Flow

```python
try:
    source = file_path.read_text()
    tree = ast.parse(source, filename=str(file_path))
    # ... analyze tree ...
except SyntaxError as e:
    raise ParseError(
        file_path=file_path,
        line=e.lineno,
        column=e.offset,
        message=e.msg,
        text=e.text
    )
```

## Error Message Format

```
ERROR: Failed to parse Python file
  File: src/jig/core/graph.py
  Line: 42, Column: 5

  Syntax error: invalid syntax

      40 |     def add_node(self, node: Dict) -> None:
      41 |         """Add a node to the graph."""
    > 42 |         if node["id"] in self.nodes
      43 |             return
      44 |

  Expected ':' after 'if' condition.

Build failed. Fix syntax errors and try again.
```

## Exit Codes

- `0`: Success (all files parsed, graph written)
- `1`: Parse error (one or more files failed to parse)
- `2`: IO error (can't read file, can't write output)
- `3`: Validation error (invalid decorator syntax, bad spec ID, etc.)

## Rationale

Fail-fast error handling is critical for:
1. **Correctness**: Partial graphs are worse than no graph (incomplete data → wrong conclusions)
2. **Developer experience**: Clear errors → fast debugging → less frustration
3. **CI integration**: Non-zero exit code stops build → catch errors early
4. **Trust**: Strict validation builds confidence in graph accuracy

The file:line:column format is an informal standard that most tools understand:
- Editors: VS Code, Vim, Emacs can jump to errors
- CI systems: GitHub, GitLab can annotate code with errors
- Terminals: Some terminals make file paths clickable

## Common Parse Errors

1. **Syntax errors**: Missing colons, mismatched brackets, invalid indentation
2. **Encoding errors**: File not valid UTF-8
3. **Python version incompatibility**: Code uses syntax not supported by analyzer's Python version
4. **Corrupted files**: Incomplete file, binary data in .py file

## Future Enhancements (V2+)

- `--lenient` mode: Skip unparseable files with warning, continue analysis
- Suggestions: Use AI to suggest fixes for common syntax errors
- Batch reporting: Report all parse errors at once, not just first failure
- Partial analysis: Analyze successfully parsed portions of file with syntax errors
